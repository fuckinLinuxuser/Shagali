# Бэкапы БД

Скрипт `astro/public/api/_backup.php` делает дамп всей БД (схема + данные) в `<backup_dir>/shagali-ГГГГММДД-ЧЧММСС.sql.gz`
с правами 600 и удаляет дампы старше `backup_keep_days` (по умолчанию 14). Запускается только из консоли (по HTTP отдаёт 403).
Дамп содержит персональные данные: папка — вне `www/`, наружу не отправлять (152-ФЗ).

## Настройка на проде (один раз)

1. В `/var/www/u3413841/data/shagali-config.php` добавить `'backup_dir' => '/var/www/u3413841/data/backups'` (папка вне корня сайта;
   скрипт создаст её сам с правами 700).
2. В панели reg.ru → «Планировщик задач (cron)» добавить ежедневную задачу (например, в 03:30):
   ```
   php /var/www/u3413841/data/www/shagali.ru/api/_backup.php
   ```
   Версию PHP выбрать ту же, что у сайта. Вывод скрипта — путь к созданному файлу; ошибки — в stderr (cron пришлёт письмо).
3. Проверить вручную один раз: запустить команду, убедиться, что файл появился и не пустой.

## Восстановление

```bash
gunzip -c shagali-20261210-033000.sql.gz | mysql -u USER -p DB_NAME
```
Дамп содержит `DROP TABLE IF EXISTS` + `CREATE TABLE` + `INSERT` по всем таблицам, поэтому восстанавливается и в пустую базу, и поверх.

## Проверено автоматически

`tests/e2e/backup.spec.ts`: дамп разворачивается в чистую базу `shagali_restore` на стенде, строки совпадают (NULL, кавычки, обратный слэш, кириллица),
хеши паролей целы; ротация удаляет старые файлы; по HTTP дамп не отдаётся.
Ручная проверка из плана 5.3 («ЛК работает на восстановленных данных») — на проде после первого дампа.
