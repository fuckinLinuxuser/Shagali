# CLAUDE.md — сайт продюсерского центра Шагали

Этот файл читается в начале каждой сессии. План работ и тесты по этапам — в `docs/PLAN.md`.
Задачи там пронумерованы (0.1, 1.3, …); эти же номера стоят в трекере прогресса.

## Проект

Сайт продюсерского центра Елены Шагали (shagali.ru): презентация спектаклей, гастрольный
план «город → дата → спектакль», продажа билетов через виджет cbiletom, формы, личный
кабинет с промокодами. Заказчик — знакомый, но работаем как с настоящим: всё, что
видит посетитель, проходит проверку.

Сроки: витрина в проде **3 декабря 2026**, личный кабинет — **16 декабря 2026**.
С 19 по 25 декабря у разработчика сессия — после 16 декабря не планировать ничего нового.

## Стек и окружение

- Сайт — Astro 6 в `astro/`, `output: 'static'`, `build.format: 'directory'`, `trailingSlash: 'never'`.
- Динамика — PHP-скрипты в `astro/public/api/` (раньше был один `public/api.php` для постов).
  Node на сервере нет: всё, что выполняется на сервере, пишется на PHP.
- Хостинг — reg.ru, виртуальный хостинг: Apache + PHP + MySQL. Корень сайта:
  `/var/www/u3413841/data/www/shagali.ru/`.
- Деплой — GitHub Actions (`.github/workflows/deploy.yml`): пуш в `main` → сборка → rsync
  с `--delete`. **`main` = прод.** Исключения rsync — `.github/rsync-excludes.txt`.
- Билеты — cbiletom.ru: iframe `https://cbiletom.ru/widget/1/frame.php?id=<eventId>&mode=1`.
  Публичного API у cbiletom нет, данных о покупках сайт не получает.
- Аналитика — Яндекс.Метрика (по ТЗ). Google Analytics и GTM убираем на этапе 2.

## Команды

Все команды выполняются из `astro/`, если не сказано иное.

```
npm run dev          # дев-сервер Astro (без PHP)
npm run build        # сборка в astro/dist
npm test             # Vitest: данные, схемы, утилиты
npm run test:e2e     # Playwright против docker-стенда (статика + PHP + MySQL)
npm run lint:php     # php -l по всем файлам в public/api
npm run check:links  # битые ссылки и href="#" в dist
npm run lhci         # Lighthouse CI по ключевым страницам
docker compose up -d # из корня репо: локальный стенд Apache+PHP+MySQL на :8080
```

Если команды ещё нет в `package.json` — она заводится на этапе 0, см. `docs/PLAN.md`.

## Как работать над задачей

1. Прочитай задачу в `docs/PLAN.md` целиком, включая блок «Проверки».
2. Перед кодом коротко напиши план: какие файлы меняются, что может сломаться.
   Если задача меняет больше 5 файлов или схему БД — дождись подтверждения.
3. Работай в ветке `feat/<номер>-<кратко>`, например `feat/1.3-city-pages`. В `main` напрямую не пушить.
4. Сначала тесты из блока «Проверки», потом реализация. Тест должен падать до изменений.
5. Задача готова, только если выполнено всё из «Definition of done» ниже.
6. В конце сессии — короткий отчёт: номера закрытых задач, что проверено руками,
   что осталось, какие решения нужны от заказчика. Без пересказа диффа.

## Definition of done

- `npm run build`, `npm test`, `npm run test:e2e`, `npm run lint:php` — зелёные.
- Все проверки из блока задачи пройдены; ручные — отмечены в отчёте как «проверено вручную».
- В консоли браузера нет ошибок на затронутых страницах.
- Новые страницы проверены на ширине 375px и 1440px.
- Нет секретов в коде (см. «Безопасность»), нет `console.log`, нет «рыбы» и `href="#"`.

## Данные

- Единственный источник правды о спектаклях и показах — коллекции в `astro/src/content/`
  (`shows`, `performances`, `cities`) со схемами zod. Компоненты не хранят своих копий данных.
- Показ: `id`, `show` (ссылка на спектакль), `city`, `date` (ISO), `time`, `venue`, `address`,
  `cbiletomId` (число или null), `status` (`on_sale` | `sold_out` | `soon` | `past`), `priceFrom`.
- Если в данных ошибка, сборка должна падать, а не рендерить пустую карточку.

## Безопасность — не обсуждается

- **Никаких секретов в репозитории и в клиентском коде.** Репозиторий публичный.
  Пароли, токены, доступы к БД — только в `config.php` вне корня сайта:
  `/var/www/u3413841/data/shagali-config.php` (на проде), `docker/config.local.php` (локально, в .gitignore).
  Старый токен админки скомпрометирован (он в истории git) — его нельзя использовать нигде.
- SQL — только PDO и подготовленные запросы. Никакой конкатенации пользовательского ввода.
- Пароли — `password_hash` / `password_verify`. Сессии: `httponly`, `secure`, `samesite=Lax`,
  `session_regenerate_id` после входа.
- Каждый POST из ЛК и админки — с CSRF-токеном. Публичные формы — honeypot + проверка времени
  заполнения + лимит запросов с IP.
- Вывод пользовательских данных — только экранированный (`htmlspecialchars` в PHP, без `set:html` в Astro).
- CORS — только свой домен. Никакого `Access-Control-Allow-Origin: *` на методах записи.
- Закрытый контент (закулисье) не кладётся в `dist` как статика: он отдаётся через PHP
  после проверки сессии. Всё, что лежит в `dist`, публично.

## Персональные данные (152-ФЗ)

- ПДн хранятся только в MySQL на reg.ru (сервер в РФ). Не отправлять их в сторонние сервисы,
  логи, URL-параметры, Метрику.
- Каждая форма с ПДн — обязательный чекбокс согласия со ссылкой на `/consent` и `/privacy`.
  В БД пишется факт согласия, время и версия текста политики.
- Метрика загружается только после согласия в cookie-баннере.
- У пользователя ЛК есть удаление аккаунта, которое реально удаляет его данные.

## Чего не делать

- Не пушить в `main` и не менять секреты GitHub Actions.
- Не добавлять зависимости без причины, которую можно назвать одной фразой.
- Не коммитить исходники фото и видео: они исключены в `.gitignore` и лежат на сервере.
- Не трогать `rsync --delete`, не добавив в `rsync-excludes.txt` всё, что живёт только на сервере
  (`posts.json`, `images/`, `videos/`, загрузки).
- Не делать визуальный редизайн «заодно». Стиль сайта уже есть, новые блоки повторяют его.
- Не придумывать тексты от имени заказчика. Нет контента — плейсхолдер с пометкой `TODO(контент)`,
  который тест `check:content` не пропустит в прод.
